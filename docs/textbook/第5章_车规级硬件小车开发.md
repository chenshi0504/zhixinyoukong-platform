# 第5章 车规级硬件小车开发

## 学习目标

通过本章的学习，读者应能够：

1. 理解车规级硬件小车在车路云一体化实验教学中的作用，掌握实体平台开发的基本边界与工程流程。

## 5.1 系统架构与开发边界

### 5.1.1 实体平台的教学价值

在智能交通与自动驾驶教学中，仿真环境能够帮助学生快速理解算法流程，但只有把算法部署到实体小车上，才能真正感受到工程实现的复杂性。真实平台中的传感器存在噪声与时延，底盘控制受通信链路和执行机构约束，坐标系和模块依赖关系也必须严格管理。因此，实体平台开发并不是对仿真的简单重复，而是把理论知识转化为工程能力的关键环节。

本章所讨论的“车规级硬件小车开发”，强调的是接近车载电子系统的组织方式，而不是狭义上的整车认证。当前平台在结构上已经具备底层驱动、定位感知、场景理解、规划控制与安全裁决等典型层次，能够比较完整地呈现车路协同系统从“数据输入”到“动作输出”的全链条过程。这使得它非常适合承担教学中的综合实验与工程训练任务。

### 5.1.2 分层架构与主链数据流

当前小车系统采用基于 ROS1 Noetic 的分层架构。底层由底盘、CAN 接口、激光雷达、IMU 和相机等硬件组成；中间层负责定位、点云配准、视觉语义映射与场景组织；上层则承担目标生成、局部规划、速度控制与安全防护等任务。分层设计的意义在于将复杂系统拆解为若干可观测、可替换、可单独调试的模块，从而降低系统联调难度。

从主链数据流看，RoboSense 激光雷达与 Hipnuc IMU 首先进入 `FAST-LIO`，生成 `/Odometry`、`/cloud_registered_body` 和 `/path` 等定位结果；前视相机链再将彩色图、深度图与点云结果融合，生成语义点云和语义地图；上层场景理解模块进一步把这些中间结果组织成场景图、地图上下文和对象记忆；最终，局部规划器和跟踪控制器把活动目标转换为速度命令，再经过安全守门模块形成可执行的 `cmd_vel_safe` 并发送到底盘。整条链路体现了实体系统开发的核心思想：上层建议不能越级直接控车，任何动作都必须经过规划、控制和安全裁决后才能执行。

从运动学角度看，小车在平面内的基础状态演化可近似写为：

$$
\dot{x}=v\cos\theta, \quad \dot{y}=v\sin\theta, \quad \dot{\theta}=\omega
\tag{5-1}
$$

式中，$x$ 和 $y$ 为平面位置，$\theta$ 为航向角，$v$ 为线速度，$\omega$ 为角速度。这个模型虽然简化，但足以说明控制器并不是直接指定车辆位置，而是通过不断调整速度指令，使车辆在反馈闭环中逼近期望轨迹。

### 5.1.3 安全边界与实时性要求

实体平台开发与纯软件实验最大的区别，在于错误不仅会导致结果异常，还可能引发硬件风险。因此，安全边界必须在系统设计阶段就被明确下来。当前小车系统中，上层语义推理输出的是结构化建议，真正送到底盘执行的是 `waypoint_follower_node` 生成的 `cmd_vel_raw`，并且它还必须经过 `safety_guard_node` 二次裁决，才会形成最终的 `cmd_vel_safe`。这一结构保证了“建议层”和“执行层”相互分离，使系统具有更好的可解释性和可控性。

与此同时，实体系统还必须满足实时性要求。一次完整控制闭环的总延迟可以抽象表示为：

$$
T_{loop}=T_{sense}+T_{fusion}+T_{plan}+T_{control}+T_{comm}
\tag{5-2}
$$

其中，$T_{sense}$ 表示采集时间，$T_{fusion}$ 表示融合处理时间，$T_{plan}$ 表示规划或推理耗时，$T_{control}$ 表示控制计算时间，$T_{comm}$ 表示通信与执行延迟。若总延迟过大，即便算法逻辑正确，也可能出现控制滞后、轨迹振荡或安全距离不足等问题。因此，实体开发不仅要关注“算得对”，还要关注“来得及算”。

## 5.2 关键硬件与通信机制

### 5.2.1 底盘、CAN 与执行链

小车底盘是所有控制动作的最终执行者。当前平台通过 CAN2USB 设备把底盘控制器映射为 Linux 下的 `can0` 网络接口，再由 `ranger_base_node` 负责与底盘驱动器通信。对于上层系统而言，底盘表现为一个能够接收速度命令并回传里程计与状态信息的执行单元；而对于底盘本身而言，系统工作模式、通信状态与硬件反馈同样是控制闭环的一部分。正因为如此，底盘驱动节点既是协议翻译器，也是执行反馈器，它把物理世界与软件系统连接成一个可观测的整体。

### 5.2.2 传感器与主定位链

当前平台的核心传感器包括 RoboSense 激光雷达、Hipnuc IMU 和 RealSense 深度相机。激光雷达提供环境几何结构，IMU 提供姿态变化和惯性信息，相机则提供彩色图像与深度图。三类传感器分别覆盖几何、惯性和视觉三个维度，共同支撑定位、建图与语义理解。

在定位链中，`FAST-LIO` 负责将激光雷达和 IMU 紧耦合融合，输出主位姿与配准点云。这意味着系统中的定位并不是某个单一传感器“直接给出”的，而是多源测量统一估计后的结果。联调时如果只关心“有没有 odom”，而不区分 `/Odometry`、`/ranger_base_node/odom` 等不同位姿链的职责，就很容易出现地图看似正常但控制方向错误的情况。因此，实体平台开发必须从一开始就建立“多源定位、分链使用”的概念。

### 5.2.3 ROS 话题、TF 与外部接口

ROS 系统中的模块协作主要依赖话题、TF 和参数服务器。话题负责传输数据流，TF 负责维护坐标变换关系，参数和 launch 文件负责描述系统如何被装配起来。对于实体小车开发而言，理解数据“是什么”与数据“在哪个坐标系里”同等重要。如果只看消息内容而忽略坐标关系，就可能出现语义地图、控制里程计与底盘姿态彼此不一致的情况。

在当前平台中，联调时最值得优先观察的话题包括 `/rslidar_points`、`/IMU_data`、`/Odometry`、`/cloud_registered_body`、`/frontview_mask_rgbd/lidar_semantic_map`、`/semantic_nav/active_waypoint`、`/semantic_nav/cmd_vel_raw` 与 `/cmd_vel_safe`。这些话题恰好构成了从感知、定位到控制执行的关键拐点。只要能够确认这些拐点是否存在、频率是否稳定、参考系是否合理，故障定位通常就能迅速收敛。

### 5.2.4 启动顺序与环境准备

实体系统开发强调规范的启动顺序。推荐的顺序是：先初始化 ROS 工作区环境，再准备 `can0`，随后启动激光雷达和 IMU，确认原始数据正常后再拉起 `FAST-LIO`，之后启动前视语义映射模块，最后才进入整链导航与安全控制。这样做的原因并不只是“习惯如此”，而是每一层都依赖上一层的输入；如果底层尚未准备好就直接启动上层模块，往往会造成设备占用、初始化超时或输入缺失等连锁故障。

每个终端在开始工作前，建议先执行统一的环境初始化命令：

```bash
cd /home/nvidia/agilex_ws
source /opt/ros/noetic/setup.bash
source /home/nvidia/agilex_ws/devel/setup.bash
```

对于教学实验而言，这一规范本身就是开发能力的一部分。能够保证所有终端环境一致，意味着后续观察到的差异更可能来自系统本身，而不是来自人为配置混乱。

## 5.3 车规级硬件小车开发方法

### 5.3.1 模块化联调流程

实体小车开发不适合采用“所有模块一起启动，哪里出错修哪里”的方式。更有效的方法是模块化联调，即按照依赖关系自底向上逐层验证。第一步确认物理接口可用，例如 `can0` 是否建立成功、雷达与 IMU 是否稳定发布数据；第二步确认主定位链正常，即 `FAST-LIO` 是否持续输出 `/Odometry` 与配准点云；第三步确认前视语义映射模块能够消费图像、深度和点云，并生成语义地图；第四步才检查活动目标、原始速度和安全速度是否构成完整控制闭环。

这种方法的优势在于，任何一层出现异常时，开发者都知道应当向前回溯哪个输入，而不是在几十个节点中盲目查找。对于课程组织而言，模块化联调还便于把任务拆分为底层通信、定位建图、语义感知和控制执行等多个子任务，再通过最终集成完成整车联调。

### 5.3.2 核心命令与状态验证

实体系统开发不能只依赖图形界面观察结果，还需要通过命令行快速验证关键链路。最常用的方法包括四类：一是用 `rostopic hz` 检查频率是否稳定；二是用 `rostopic echo -n 1` 抽查消息头和关键字段；三是用 `rosnode list` 检查节点是否真正在线；四是通过发布单个目标点或急停命令验证控制链是否闭合。下面给出几条典型检查命令：

```bash
rostopic hz /rslidar_points
rostopic hz /IMU_data
rostopic hz /Odometry
rostopic echo -n 1 /frontview_mask_rgbd/lidar_semantic_map/header
rostopic echo -n 1 /semantic_nav/active_waypoint
rostopic echo -n 1 /cmd_vel_safe
rostopic hz /ranger_base_node/odom
```

如果需要验证导航链是否能够接受外部目标点，还可以在确认环境安全的前提下手动发布一个测试目标。这里的关键不只是“会不会发命令”，而是知道“在什么条件下允许发命令”。这正是实体平台开发与纯仿真操作最本质的区别。

### 5.3.3 常见故障与排查思路

实体小车联调中最常见的故障，往往不是程序完全起不来，而是“部分链路正常、部分链路异常”所形成的复杂症状。例如，底盘不动并不一定意味着底盘损坏，也可能是 `/cmd_vel_safe` 根本没有产生；语义地图漂移也不一定是感知算法本身出错，还可能是 IMU 数据异常、外参配置不一致或控制里程计使用错误所导致。要想高效定位这类问题，必须把模糊的现象描述转化为明确的链路问题。

一个实用的方法是把故障统一翻译成“哪个关键拐点的信号丢了”。如果 `can0` 正常、`ranger_base_node` 在线，但 `/cmd_vel_safe` 为空，就应把注意力放在控制与安全层；如果 `/Odometry` 正常而语义地图异常，就应重点检查相机、深度流和 TF 关系。只要能够定位到丢失的拐点，问题范围通常会迅速缩小。

### 5.3.4 实验报告与工程规范

在教学场景下，硬件实验不仅要追求结果，还要重视过程记录。建议学生按照“系统配置—启动顺序—关键观测—问题现象—定位过程—解决方法—实验结论”的结构撰写实验报告。这样的报告方式能够体现真实的工程调试过程，而不是把实验写成单纯的操作清单。

从工程规范角度看，实体平台开发至少应遵守三项基本要求：第一，所有关键命令和节点状态要留痕，便于复盘；第二，任何运动测试都必须在确认急停手段可用后进行；第三，涉及坐标系、外参和运行模式的配置修改应明确记录版本与修改理由。对于硬件开发而言，规范并不是附属品，而是保证系统可重复、可维护、可教学的基础条件。

## 5.4 实验九：底层链路准备实验

### 5.4.1 实验目的

本实验旨在帮助读者完成实体小车开发的第一步，即建立稳定可靠的底层硬件链路。通过本实验，读者应能够掌握 ROS 工作区环境初始化方法，完成 `can0` 的拉起与状态检查，启动激光雷达和 IMU 并确认其输出正常，同时理解底层链路在后续定位与控制实验中的基础作用。

### 5.4.2 实验原理

实体小车的所有上层能力都建立在底层链路之上。对于当前平台而言，底层链路至少包括两部分：其一是底盘通信链，即 CAN2USB、`can0` 和底盘驱动节点之间的连接；其二是基础感知链，即 LiDAR 和 IMU 的数据采集与发布。如果这两部分没有准备好，后续定位、感知与控制模块就失去了输入基础，因此本实验的目标不是让小车立即运动，而是建立可供后续模块依赖的系统底座。

### 5.4.3 实验步骤

首先在每个终端中完成环境初始化，确保 ROS 基础环境和工作区环境都已被正确加载。随后重新拉起 `can0` 并检查接口状态，再分别启动激光雷达和 IMU 节点，通过话题频率确认原始数据稳定发布。建议在实验过程中同步记录 `can0` 状态、`/rslidar_points` 频率和 `/IMU_data` 频率，为后续实验提供基准。

```bash
bash /home/nvidia/agilex_ws/src/ranger_ros/ranger_bringup/scripts/bringup_can2usb.bash
ip -details link show can0
roslaunch ranger_bringup open_lidar.launch
rostopic hz /rslidar_points
roslaunch hipnuc_imu imu_msg.launch
rostopic hz /IMU_data
```

### 5.4.4 结果分析与讨论

完成实验后，需要重点分析三个问题。第一，`can0` 是否处于正常工作状态；第二，LiDAR 和 IMU 数据是否持续发布且频率稳定；第三，当前在线节点是否与预期一致。实验分析不应只写“成功”或“失败”，而应明确说明哪些接口正常、哪些数据可用、哪些环节仍存在隐患。只有这样，这一实验结果才能成为后续联调的有效基线。

## 5.5 实验十：定位与语义感知联调实验

### 5.5.1 实验目的

本实验旨在帮助读者建立从原始传感器数据到环境理解结果的完整认识。通过本实验，读者应能够启动 `FAST-LIO` 并验证主定位链是否正常工作，理解 `/Odometry` 与 `/cloud_registered_body` 的作用，能够拉起前视语义映射模块并检查语义点云、语义地图的输出，同时初步掌握坐标关系和外参一致性对系统稳定性的影响。

### 5.5.2 实验原理

`FAST-LIO` 通过激光雷达和 IMU 的紧耦合融合，解决的是“小车在哪里、姿态如何、空间结构怎样”的问题；前视语义模块则把图像、深度图和点云对齐，生成语义点云和语义地图，为上层场景理解提供输入。如果定位链不稳定，语义结果就会漂移；如果坐标关系不一致，即使各模块都有输出，系统也无法得到可信的环境表示。因此，本实验关注的不只是“模块是否启动”，更关注“结果是否对齐且可解释”。

### 5.5.3 实验步骤

在底层链路正常的前提下，首先启动 `FAST-LIO` 并确认 `/Odometry` 与 `/cloud_registered_body` 稳定发布。随后配置视觉运行环境，必要时清理旧的相机与前视语义残留进程，最后启动前视语义映射模块，并检查彩色图、深度图和语义地图是否正常输出。如果条件允许，还应在可视化工具中观察配准点云与语义地图是否保持一致。

```bash
roslaunch fast_lio mapping_robosenseM1.launch
rostopic hz /cloud_registered_body
rostopic hz /Odometry
export LD_LIBRARY_PATH=/home/nvidia/.local/opencv42/usr/lib/aarch64-linux-gnu:$LD_LIBRARY_PATH
roslaunch frontview_mask_rgbd_ros frontview_mask_rgbd_recorded_realsense_fastlio.launch
rostopic hz /camera/color/image_raw
rostopic echo -n 1 /frontview_mask_rgbd/lidar_semantic_map/header
```

### 5.5.4 结果分析与讨论

本实验的关键结果包括三项：一是主定位链是否稳定；二是相机彩色流和深度流是否连续；三是语义地图的消息头与参考系是否合理。如果出现“定位正常但语义缺失”的情况，应优先检查相机与前视模块；如果出现“语义有了但位置明显漂移”的情况，则应回头检查 TF 外参关系与定位输出质量。对本实验的评价，不应停留在“看到了地图”这一层面，而应进一步判断地图是否稳定、是否对齐、是否能够为后续决策提供可信输入。

## 5.6 实验十一：安全控制与导航闭环实验

### 5.6.1 实验目的

本实验旨在帮助读者理解实体小车从“有感知、有定位”走向“可安全运动”的关键步骤。通过本实验，读者应能够理解 `active_waypoint -> cmd_vel_raw -> cmd_vel_safe -> 底盘` 的控制闭环，能够启动完整导航链并检查关键控制话题，能够通过手动目标点验证规划与控制链是否真正打通，同时掌握软件急停与复位的基本操作。

### 5.6.2 实验原理

在当前平台中，局部规划器首先给出活动目标，`waypoint_follower_node` 根据目标点和当前位姿计算原始速度指令 `cmd_vel_raw`，随后 `safety_guard_node` 再结合风险状态和限速条件进行裁决，形成最终送到底盘执行的 `cmd_vel_safe`。这意味着，底盘是否运动，并不只取决于上层是否生成目标，而取决于整条执行链是否完整、状态是否允许。控制实验的意义就在于把“系统看起来有决策”与“系统确实能安全执行”区分开来。

### 5.6.3 实验步骤

在确认周围环境安全、急停手段可用、定位与语义链正常后，拉起完整导航链并检查活动目标、原始速度和安全速度等关键话题。随后手动发布一个近距离测试目标，观察 `active_waypoint`、`cmd_vel_raw` 与 `cmd_vel_safe` 是否按顺序变化，并结合底盘里程计判断执行结果是否符合预期。如果实验中出现异常，应立即执行急停并回到逐层排查模式。

```bash
rostopic echo -n 1 /semantic_nav/active_waypoint
rostopic echo -n 1 /semantic_nav/cmd_vel_raw
rostopic echo -n 1 /cmd_vel_safe
rostopic hz /ranger_base_node/odom
rostopic pub -1 /semantic_nav/goal geometry_msgs/PoseStamped '{header: {frame_id: camera_init}, pose: {position: {x: 1.0, y: 0.0, z: 0.0}, orientation: {x: 0.0, y: 0.0, z: 0.0, w: 1.0}}}'
```

### 5.6.4 结果分析与讨论

如果目标点成功发布且底盘按预期短距离运动，说明导航闭环已经打通；如果 `active_waypoint` 存在但 `cmd_vel_raw` 为空，问题通常出在跟踪控制器；如果 `cmd_vel_raw` 存在而 `cmd_vel_safe` 被压制，则需要检查安全守门条件；如果 `cmd_vel_safe` 已经生成但底盘无动作，则应继续检查 `ranger_base_node` 与底盘通信状态。通过这样的分层分析，读者可以真正掌握实体平台控制闭环的诊断方法，而不是停留在“节点都开起来了”的表面判断上。

## 5.7 例题与思考

### 5.7.1 例题一：启动顺序设计

#### 例题一的题目描述

某实验小组计划进行实体小车联调，已知硬件包括底盘、LiDAR、IMU 和 RealSense，相应软件模块包括底盘驱动、`FAST-LIO`、前视语义映射和导航控制。请设计一个合理的启动顺序，并说明每一步的依赖关系与验证方法。

#### 例题一的解题思路

应从依赖关系出发，自底向上组织模块启动顺序。凡是为其他模块提供输入的节点，都应先于其消费者启动；每一层启动后，都要有对应的验证动作，确认链路稳定后再进入下一层。

#### 例题一的参考答案

推荐顺序为：环境初始化与 `can0` 准备；启动 LiDAR 与 IMU；启动 `FAST-LIO` 并检查 `/Odometry`；启动 RealSense 与前视语义映射并检查语义地图；最后启动导航控制并检查 `cmd_vel_raw` 与 `cmd_vel_safe`。采用这一顺序的原因在于，定位依赖原始传感器，语义依赖定位和相机，控制又依赖定位、语义和目标点。若不遵循此顺序，系统很容易因为上游输入缺失而出现级联故障。

### 5.7.2 例题二：故障定位分析

#### 例题二的题目描述

联调过程中发现：`/Odometry` 正常，语义地图也能发布，但发布测试目标后底盘没有动作。请分析可能原因，并给出排查路径。

#### 例题二的解题思路

既然定位与语义链正常，问题应重点集中在控制闭环。排查应沿 `active_waypoint -> cmd_vel_raw -> cmd_vel_safe -> ranger_base_node -> 底盘` 逐层向后推进，而不是重新回到底层传感器。

#### 例题二的参考答案

首先检查 `/semantic_nav/active_waypoint` 是否存在，确认目标点是否真正被规划器接受；若有目标但没有 `cmd_vel_raw`，则应检查跟踪控制器状态；若 `cmd_vel_raw` 存在而 `cmd_vel_safe` 为空，则应查看安全守门模块是否触发了限速或急停条件；若 `cmd_vel_safe` 已存在但底盘无动作，则需要继续检查 `can0`、`ranger_base_node` 和底盘执行状态。该故障的关键不在于“系统哪儿都可能有问题”，而在于按控制主链逐层缩小范围。

### 5.7.3 思考题

Q5.2 在同一套系统中同时存在 `/Odometry`、`/ranger_base_node/odom` 等位姿链时，为什么不能简单地把它们视为等价输入？

本章围绕车规级硬件小车开发，系统介绍了实体平台在教学中的定位、系统分层结构、关键硬件组成、ROS 通信机制以及安全控制边界。与纯仿真相比，实体平台开发更强调依赖关系、时序约束、坐标一致性和安全守门机制，这些因素共同决定了系统能否从“有算法”真正走向“可运行”。
